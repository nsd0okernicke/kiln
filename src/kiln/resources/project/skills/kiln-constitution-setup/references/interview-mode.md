# Interview mode

Interview one decision at a time. Include a recommended answer and its trade-off. Skip anything
already established by repository evidence or earlier answers.

Cover only the areas needed to make the two constitution files actionable:

1. Project purpose, intended users, core capabilities, and deliberate exclusions.
2. Languages, supported runtime versions, frameworks, and dependency/environment management.
3. Architecture style, dependency direction, modules or bounded contexts, and their ownership.
4. Persistence, messaging, external services, and integration boundaries.
5. Exact build, test, lint, format, type-check, coverage, and mutation commands that will be
   required; mark a category not applicable rather than inventing a tool.
6. Quality thresholds, contribution practices, platform constraints, and operational limits.

Do not write the final files while a material answer remains unknown. If the user deliberately
defers a decision, omit the unsupported rule and record the omission in the proposal rather than
placing `TBD`, angle-bracket placeholders, or guesses in the constitution.
